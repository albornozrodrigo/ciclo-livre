<objective>
## Goal
Abrir no app um banco SQLite **comprovadamente criptografado**:
- chave aleatória de 256 bits gerada no primeiro uso e guardada no `expo-secure-store` (Android Keystore);
- `PRAGMA key` aplicado logo após abrir, antes de qualquer leitura;
- falha explícita se o SQLCipher não estiver ativo (`PRAGMA cipher_version` vazio), em vez de gravar dados em claro;
- executor de migrations versionado por `PRAGMA user_version`, cada migration numa transação.

## Purpose
Dados de saúde reprodutiva são sensíveis (LGPD). Toda fase seguinte grava no banco, então a criptografia precisa existir e estar provada antes do primeiro registro.

## Output
- Módulos `src/db/` testados com TDD (testes em Node usando `node:sqlite` real para as migrations).
- `SQLiteProvider` no layout raiz com inicialização (chave → verificação → migrations).
- Evidência no aparelho: o arquivo do banco não começa com o cabeçalho `SQLite format 3`.
</objective>

Docs (Context7 `/expo/expo`, expo-sqlite):
- SQLCipher exige `useSQLCipher: true` no config plugin e build nativo; não funciona no Expo Go.
- `PRAGMA key` não aceita parâmetro ligado: usar o formato de chave bruta `x'<64 hex>'` com validação estrita (regex), nunca interpolar entrada arbitrária.
- `withExclusiveTransactionAsync()` abre outra conexão sem a chave: **proibido** neste projeto; usar `withTransactionAsync()`.
- Habilitar SQLCipher não criptografa banco já existente em claro (não há dados ainda; app nunca gravou banco).
</context>

<acceptance_criteria>

## AC-1: Chave gerada uma vez e guardada no secure-store
```gherkin
Given um secure-store vazio
When getOrCreateDatabaseKey() é chamado duas vezes
Then a primeira chamada gera 32 bytes aleatórios, grava como 64 hex minúsculos e devolve
And a segunda devolve a mesma chave sem gerar outra
And um valor corrompido no store (não-hex ou tamanho errado) gera erro, sem sobrescrever
```

## AC-2: Migrations versionadas e atômicas
```gherkin
Given um banco novo (user_version = 0) e a lista de migrations
When runMigrations roda
Then todas as migrations com versão > user_version aplicam em ordem, cada uma numa transação
And user_version termina igual à maior versão
And rodar de novo não aplica nada
And uma migration que falha desfaz só a sua transação, mantém user_version anterior e propaga o erro
And versões duplicadas ou fora de ordem na lista geram erro antes de aplicar qualquer coisa
```

## AC-3: Abertura segura
```gherkin
Given uma conexão recém-aberta
When initDatabase(db) roda
Then executa PRAGMA key com a chave validada antes de qualquer outra instrução
And falha com DatabaseNotEncryptedError se PRAGMA cipher_version vier vazio
And depois habilita foreign_keys e roda as migrations
And nenhuma mensagem de erro ou log contém a chave
```

## AC-4: Criptografia comprovada no aparelho
```gherkin
Given o dev build reconstruído com useSQLCipher
When o app abre no RQCRA00XP8N
Then logcat não mostra erros de JS
And os 16 primeiros bytes do arquivo do banco (via run-as) não são "SQLite format 3\0"
```

## AC-5: Qualidade
```gherkin
When rodo npm test, npx tsc --noEmit e npx expo lint
Then tudo passa
```
</acceptance_criteria>
